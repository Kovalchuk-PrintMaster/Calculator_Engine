## Принципи команди

* **Малими кроками.** Кожна зміна — невелика, із тестами і поясненням.
* **Прозорість.** Усі рішення фіксуємо у `docs/` (ADR). Важливі дії — у `docs/notes/session-log.md`.
* **Автоматизація.** Будь‑яка повторювана операція → в `Makefile` і/або CI.
* **Спостережуваність.** Логи, request_id, метрики — з першого дня.
* **Захист від зламу.** Найменші привілеї, відсутність секретів у коді, репродуктивні середовища.

## Словник термінів

* **Calculator Engine** — бекенд‑движок для ціноутворення поліграфічних продуктів.
* **Quote** — розрахунок ціни (вхідні параметри + алгоритм ціноутворення → відповідь).
* **Audience** — сегмент клієнтів (наприклад, `retail`, `wholesale`).
* **request_id** — унікальний ідентифікатор запиту; використовується для кореляції логів.
* **CI/CD** — безперервна інтеграція/доставлення (GitHub Actions).

## Архітектурні орієнтири

Деталі — у `docs/architecture/02-architecture.md`.

* Шарова архітектура: **app (FastAPI)** → **domain (бізнес‑логіка)** → **infra (DB/cache/IO)** → **shared/config**.
* Чіткі контракти між шарами (Pydantic моделі/TypedDict/протоколи).
* Мінімізуємо зв’язність: бізнес‑логіка не знає про FastAPI/SQLAlchemy напряму.
* Трасування запитів: middleware додає `X-Request-ID` + контекст `REQUEST_ID_VAR`.

## Правила для файлів/скриптів (шаблон шапки)

> **Застосовуємо до всіх нових файлів.** Шапка допомагає через роки швидко зрозуміти призначення.

```python
"""
Назва скрипту: <ім'я_файлу.py>

Детальний опис:
  - Що робить, яка логіка, який результат очікується.

Прямі залежності від цього скрипту:
  - <файл/модуль1>, <файл/модуль2>

Вхідні залежності (від чого залежить цей скрипт):
  - <файл/модульA>, <зовнішній сервіс/бібліотека>

Неявні шляхи (якщо є):
  - /home/printmaster/calculator_engine/logs/...

Логування:
  - Ключові етапи + статуси; для критичних шляхів — CSV у `logs/`.

Примітки з експлуатації:
  - Потенційні ризики/обмеження, як відновити після збою.
"""

# Далі — сам код з детальними коментарями до констант і функцій
```

## Код-стайл і статичний аналіз

* **black** — форматування (`make fmt`, `make fmt-check`).
* **ruff** — лінтер + автофікс (`make lint`, `make lint-fix`).
* **mypy** — статичні типи (`make mypy`). Конфіг — у `pyproject.toml`.
* **pre-commit** (опційно, можна додати окремим кроком) — локальна перевірка перед коммітом.

## Гілки, комміти, PR, релізи

* **Гілки:** `main` (stabile), `feat/*`, `fix/*`, `docs/*`.
* **Комміти:** `type: коротко про зміну` (напр., `feat: add /price/quote stub`).
* **PR:** маленькі, із описом *що/навіщо/як перевірити*. Автоперевірки: ruff, black --check, mypy, pytest.
* **Релізи:** теги `vX.Y.Z`. Версіонування — SEMVER. Зміни описуємо в `CHANGELOG.md` (можемо підключити `keep-a-changelog`).

## Тестування й покриття

* Команди: `make testv`, `make test-cov`, `make test-fast`.
* Піраміда: unit → service (router/middleware) → інтеграційні (DB/Redis) → e2e.
* Бібліотеки: `pytest`, `pytest-xdist`, `pytest-cov`, `pytest-randomly`.
* Покриття як ціль: спочатку 80%+, далі — підвищуємо на критичних модулях.

## Логування та спостережуваність

* Root‑логер ініціалізується в `app/main.py` через `setup_logging()`.
* **RequestIdFilter** додає `record.request_id` з `REQUEST_ID_VAR`.
* Форматери: `PlainFormatter` (консоль) і `CsvFormatter` (файл `logs/app.csv`).
* Маршрути:

  * `X-Request-ID` генерується або підхоплюється middleware і додається у відповідь.
  * У тестах `caplog` бачить записи (бо root налаштовано і рівні NOTSET для дочірніх логерів).
* Додаткові каталоги логів: `logs/autentification`, `logs/data_base`.

## Налаштування середовищ

* **Файли TOML:** `config/base.toml`, `config/dev.toml`, `config/prod.toml`.
* **ENV:** `ENV=dev|prod|test`, `DEBUG=1|0`, `POSTGRES_DSN`, `REDIS_URL`, ...
* **settings.py:** завантажує значення у порядку: значення за замовчуванням → base.toml → {ENV}.toml → змінні оточення.

## Секрети та безпека

* Секретів у гіт не заливаємо.
* Для локалу: `.env` (у `.gitignore`), приклад — `config/.env`.
* У продакшн: GitHub Actions Secrets / Vault / KMS.
* Найменші привілеї для БД/облікових записів; періодична ротація ключів.

## База даних і міграції

* Цільова схема та правила — у `docs/architecture/04-db.md`.
* Орм: SQLAlchemy 2.x (Declarative, async engine), міграції — Alembic.
* Локально: `docker compose -f infra/db/docker-compose.yml up -d`.
* Перевірка підключення: `make db-ping` (читає `settings.postgres_dsn`).

## API та контракти

* FastAPI, відкриті `/docs` і `/redoc` у дев‑режимі.
* Контракти фіксуємо Pydantic‑моделями (input/output), стабільні поля — покриваємо тестами.
* `GET /health`, `GET /meta/*`, `POST /price/quote` (stub) — стартовий набір.
* Мета‑роутер (`/meta`) — для службових ендпоїнтів (версія, ping, docs).
* Doctor‑роутер (`/doctor`) — технічні перевірки стану сервісу.

## Операційні процедури

* **Запуск локально:** `make run` (Uvicorn, auto‑reload). Процес «висить» у терміналі — це нормально; відкрийте нову вкладку/сесію для інших команд.
* **Хвости логів:** `make logs-tail`.
* **CI:** `.github/workflows/ci.yml` — ruff, black --check, mypy, pytest, ковередж.
* **Релізний пайплайн:** (заплановано) — теги → збірка образу → деплой.
