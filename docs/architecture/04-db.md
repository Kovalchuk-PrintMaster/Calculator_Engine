## 3) Цільова архітектура доступу до даних

### 3.1 Синхронний старт (простий шлях)

* **SQLAlchemy 2.0 (Core/ORM)** + `psycopg` (синхронний драйвер).
* `create_engine(settings.postgres_dsn, pool_pre_ping=True, pool_size=5, max_overflow=10)`.
* `Session` через `sessionmaker(bind=engine, autoflush=False, autocommit=False, expire_on_commit=False)`.
* Виклик у домені — через тонкі репозиторії/сервіси у `infra/db` (ендпоінти **не** знають про БД напряму).

### 3.2 Перехід на async (за потреби масштабування)

* Замінити на `asyncpg` або `psycopg[pool]/async` + `create_async_engine`.
* `async_sessionmaker` і `async with session.begin(): ...`.
* Ендпоінти FastAPI оголошуються як `async def` і отримують сесію через залежність (`Depends`).

### 3.3 Транзакції й шаблон доступу

* Використовуємо контекстні менеджери (`with Session.begin(): ...`).
* Явний контроль за межами транзакції; короткі транзакції; ідемпотентні повтори.
* Рівень ізоляції — за замовчуванням `READ COMMITTED`; для звітності — `REPEATABLE READ`/`SERIALIZABLE` (точково).

## 4) Цільова схема (чернетка)

Нижче — пропозиція мінімальної схеми для калькуляції друку. Розвиватимемо спільно з бізнес‑логікою `domain/pricing`.

```text
+----------------+       +-----------------+       +-----------------+
| products       |1     *| product_options |*     1| materials       |
|----------------|       |-----------------|       |-----------------|
| id (pk)        |<----->| product_id (fk) |<----->| id (pk)         |
| sku (uniq)     |       | option_id (fk)  |       | code (uniq)     |
| name           |       | value           |       | name            |
| base_unit      |       | price_delta     |       | unit            |
| base_price     |       | ...             |       | cost_per_unit   |
| ...            |       +-----------------+       | ...             |
+----------------+                                   +-----------------+
        | 1
        |                              +-----------------+
        |                              | pricing_rules   |
        |                              |-----------------|
        |                              | id (pk)         |
        |                              | product_id (fk) |
        |                              | audience (enum) |
        |                              | formula (json)  |
        |                              | active (bool)   |
        |                              | valid_from/to   |
        v                              +-----------------+
+----------------+       +-----------------+
| quotes         |1     *| quote_items     |
|----------------|       |-----------------|
| id (pk)        |<----->| quote_id (fk)   |
| created_at     |       | product_id (fk) |
| customer_ref   |       | qty             |
| currency       |       | unit_price      |
| total          |       | total_line      |
| request_id     |       | calc_meta (json)|
+----------------+       +-----------------+
```

### 4.1 Типи та конвенції

* `snake_case` для назв таблиць/полів.
* Первинні ключі — `BIGINT`/`SERIAL` (або `UUID` за потреби розподіленості).
* Посилання `*_id` з FK; `ON UPDATE RESTRICT`, `ON DELETE RESTRICT/SET NULL` — залежно від бізнес‑правил.
* Дати/час: `timestamptz` (UTC) + індекси за полями, що фільтруються.
* `audience` — `ENUM('b2c','b2b')` (узгоджено з API `/price/quote`).
* `formula` / `calc_meta` — `JSONB` для гнучких правил/проміжних обчислень.

### 4.2 Приклад DDL (чернетка)

```sql
create table products (
  id bigserial primary key,
  sku text not null unique,
  name text not null,
  base_unit text not null,             -- шт, м², пог.м
  base_price numeric(12,2) not null,
  created_at timestamptz not null default now()
);

create table materials (
  id bigserial primary key,
  code text not null unique,
  name text not null,
  unit text not null,
  cost_per_unit numeric(12,4) not null,
  created_at timestamptz not null default now()
);

create type audience as enum ('b2c','b2b');

create table pricing_rules (
  id bigserial primary key,
  product_id bigint not null references products(id),
  audience audience not null,
  formula jsonb not null,
  active boolean not null default true,
  valid_from timestamptz default now(),
  valid_to timestamptz,
  created_at timestamptz not null default now()
);

create table quotes (
  id bigserial primary key,
  created_at timestamptz not null default now(),
  customer_ref text,
  currency text not null default 'UAH',
  total numeric(14,2) not null default 0,
  request_id text
);

create table quote_items (
  id bigserial primary key,
  quote_id bigint not null references quotes(id) on delete cascade,
  product_id bigint not null references products(id),
  qty bigint not null check (qty > 0),
  unit_price numeric(12,2) not null,
  total_line numeric(14,2) not null,
  calc_meta jsonb
);

create index idx_pricing_rules_active on pricing_rules(active);
create index idx_pricing_rules_product_audience on pricing_rules(product_id, audience);
create index idx_quotes_created_at on quotes(created_at);
```

## 5) Міграції (Alembic)

* Додаємо залежність `alembic` (dev) і ініціалізуємо `alembic/`.
* Конфігуруємо `sqlalchemy.url` через `settings.postgres_dsn` або `env var`.
* Потік роботи:

  1. Оновити моделі/DDL.
  2. `alembic revision -m "add pricing tables" --autogenerate`.
  3. Перевірити скрипт, доопрацювати вручну (особливо індекси/ENUM/констрейнти).
  4. `alembic upgrade head`.
* Для тестів — окремий DSN (`ENV=test`), створення БД з нуля, `upgrade head`, далі тести.

## 6) Локальна БД (docker-compose, dev)

Приклад `docker-compose.yml` (чернетка для `deploy/compose/docker-compose.yml`):

```yaml
version: "3.9"
services:
  postgres:
    image: postgres:16
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: app
      POSTGRES_DB: calculator
    ports: ["5432:5432"]
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app"]
      interval: 5s
      timeout: 5s
      retries: 10
volumes:
  pgdata: {}
```

Після запуску: `make db-ping` має показати **DB UP** (коли налаштований `settings.postgres_dsn`).

## 7) Логування БД

* CSV‑лог у `logs/app.csv` (загальний) + за потреби окремі логи у `logs/data_base/` (див. `config/paths.py`).
* Рекомендуємо ввімкнути лог повільних запитів у Postgres (`log_min_duration_statement`).

## 8) Резервні копії (S3, опційно)

* Налаштувати `settings.s3_endpoint`, `settings.s3_bucket_backups`.
* Кроном (GitHub Actions / системний) викликати скрипт `pg_dump` → завантаження у S3.
* Політика зберігання: щоденні — 7 днів, тижневі — 4 тижні, місячні — 6 місяців (узгоджується з бізнесом).

## 9) Безпека

* Мінімальні ролі в Postgres (окремий користувач `app_ro`, `app_rw`).
* Зберігати секрети лише у `.env`/secrets, не комітити в репозиторій.
* Обмеження доступу до БД (VPC/файрвол, TLS, список дозволених IP).

## 10) Тестування даних

* Unit: мок/фейк репозиторії без БД.
* Integration: тимчасова БД (docker service) + Alembic `upgrade head` перед тестами.
* Data‑quality: перевірки констрейнтів, унікальності, консистентності.
